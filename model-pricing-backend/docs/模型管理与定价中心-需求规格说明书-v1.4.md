## 0 文档说明

### 0.1 这个系统是什么

不是"模型列表管理页"，而是整个中转平台的**模型数据中心 + 进货/出货两条定价线**：

- **进货线（成本链）**：厂商官方价 → 供应商报价 → 标准采购成本（成本基线）
- **出货线（售价链）**：标准采购成本 → 完全成本 → 毛利定价 → 对外价目表

两条线共用同一套模型档案做基准。同一个模型在系统里有三个名字，成本和售价就永远对不上账——这是此类平台最常见的崩溃点。

### 0.2 本期不做

- 实时计费扣费（属计费系统，本系统只输出价目表）
- 网关路由与负载均衡（只输出"可用供应商 + 权重建议"）
- 供应商结算与开票（只输出对账所需成本口径）
- 模型效果评测（P2 扩展的能力探测除外）

> **边界澄清（v1.4 新增）**：本系统不产生账单与扣费，但客户门户（含 H5/小程序）**只读展示**余额、授信占用、押金状态——数据由计费系统提供，本系统仅透传；结算账户、采购下单、开票均不在本期范围。

### 0.3 三条全局红线（贯穿所有用例）

1. **数据隔离**：供应商门户绝不能看到其他供应商的报价、平台对外售价、平台毛利——三类字段在接口层物理剔除，不靠前端隐藏；销售不可见成本，只暴露「最低可售价 floor」单一数值。
2. **价格不可变**：官方价、供应商报价、客户报价一律「改价 = 新建版本 + 关闭旧版本生效期」，严禁原地 UPDATE；任何历史时点的成本与售价必须可追溯。
3. **防历史改账**：报价默认以提交时刻生效；只有「成本补录」特权角色可指定过去时间（强制审计理由，`retroactive=true` 高亮），重算范围仅限「指定生效时间起至今」。

### 0.4 阅读路径

先看第 1 章（谁在用）与第 2 章（系统长什么样）；开发排期看第 3 章用例规约表（每条带 PRD 出处）；关键链路实现看第 4 章交互时序图；状态字段设计看第 5 章。与 PRD 冲突时以 PRD 原文为准；用例与 PRD 章节的映射见第 8 章追溯表。

## 1 账号、角色与权限体系（登录门户落地方案）

> 本章为登录门户的落地设计：系统使用者分三类——**内部员工**（运营/采购/定价/销售/财务/管理员）、**外部客户**、**供应商**，分别对应三个登录门户。账号体系沿用「主体 ≠ 账号 ≠ 角色」三层解耦，并新增**组织管理**与**数据权域**两套机制：角色决定「能做什么、能看多大范围」，组织位置决定「范围的具体边界」。

### 1.1 三大登录门户与账号体系

| 门户 | 使用者 | 账号类型 | 登录方式 | 登录后看到什么 |
| --- | --- | --- | --- | --- |
| **内部运营门户** | 内部员工（运营/采购/定价/销售/财务/管理员） | `internal_staff` + `account` | 工号/手机号 + 密码；企业微信扫码（P1） | 按角色渲染的菜单 + 按数据权域过滤后的数据 |
| **供应商门户** | 供应商操作员 | `legal_subject` + `supplier_profile` + `account` | 手机号 + 短信 OTP / 密码 | 仅本主体的报价、资质、对账数据 |
| **客户门户** | 客户操作员 | `legal_subject` + `customer_profile` + `account` | 手机号 + 短信 OTP / 密码 | 仅本主体的价目表、报价、合同、账单 |

| 财务 | 内部 | 汇率锁定、结算对账、授信与押金管理、第二审批人 | M10 编/对账，**M5 编（汇率锁定）+ 查**，M7 查 | ALL（成本/结算/税全量，售价只读） |

### 1.3 客户与供应商商务档案（新增：付款方式 / 授信额度 / 押金）

客户与供应商档案在身份档案之外，增加**商务与授信属性**，作为计费、风控与门户展示的依据。三类字段的变更仅财务（或客户/采购主管）可改，销售与采购只读，全部留审计。

**客户档案（customer_profile）新增**

| 字段 | 说明 | 联动规则 |
| --- | --- | --- |
| 付款方式 payment_type | 预付充值 / 后付月结 / 按量后付 | 预付：先充值后消费，余额不足自动限流；后付：消费挂账计入授信占用 |
| 授信额度 credit_limit | 平台授予的赊账上限（0 = 仅预付） | 占用 ≥ 80% 预警（通知客户 + 销售待办）；≥ 100% 冻结新调用（阈值可配），还款后自动解冻 |
| 押金 deposit_amount / deposit_status | 未缴 / 已缴 / 冻结 / 已退 | 可抵扣违约与坏账；退户结算后退还；冻结期间可限制新签合同 |
| 账期 billing_cycle | 月结 30 天等 | 与后付付款方式配套 |
| 信用状态 credit_status | 正常 / 超额预警 / 超额冻结 | 由授信占用自动驱动，冻结/解冻全部留痕 |
| 开票类型 invoice_type | 专票 / 普票 / 不需要 | 海外模型无专票时强制 flag 合规风险（见 PRD §7.0） |

**供应商档案（supplier_profile）新增**

| 字段 | 说明 | 联动规则 |
| --- | --- | --- |
| 付款方式 settlement_type | 预付充值 / 后付月结（平台对供应商） | 后付采购金额计入应付账款 |
| 账期 billing_cycle | 月结 30/45 天等 | 影响对账周期 |
| 最低起充 min_recharge | 预付型供应商的最低充值额 | 低于起充额禁止下单 |
| 押金/履约保证金 deposit_amount | 供应商向平台缴纳 | 断供/降智等违约可扣罚；余额不足预警采购 |
| 后付采购额度 credit_line | 平台对该供应商的应付账款上限 | 超额暂停新增采购下单，付款后恢复 |
| 结算状态 settle_status | 正常 / 超额预警 / 超额冻结 | 自动驱动，全程留痕 |

### 1.4 组织管理：部门树与从上往下的域覆盖

内部员工（`internal_staff`）必须挂在**组织树**（`org_unit`）上：公司 → 部门 → 小组，每个节点可设一名负责人。组织树是数据权域的边界来源：

- **普通员工**：数据域 = SELF（仅本人归属的资源，如采购员仅见本人引入的供应商、销售员仅见自身客户）。
- **部门/小组负责人**：数据域 = DEPT_SUB（本节点及**全部下级节点**的数据，从上往下递归覆盖）——采购主管看得见本组所有采购员引入的资源，销售主管看得见本组所有客户。
- **职能角色**（运营/财务/定价等）：数据域 = ALL，与所在组织位置无关。
- **调岗**：由管理员操作并留审计；历史数据归属按归属人快照不变（避免业绩/对账混乱）。

### 1.5 权限模型：角色 = 功能权限 × 数据权域 × 字段剔除

权限与角色强关联，角色装配三类规则：

1. **功能权限**：12 个功能模块 × 操作点（查看 V / 编辑 E / 审批 A / 配置 C / 特权 P），决定门户上「菜单和按钮长什么样」。
2. **数据权域**：SELF（本人归属）/ DEPT（本部门）/ DEPT_SUB（本部门及下级）/ ALL（全量），决定「能看到哪些行的数据」。
3. **字段级剔除**：成本、毛利等敏感字段对销售、供应商在接口层物理剔除（不靠前端隐藏）。

**实际可见范围 = min（角色声明的数据域，组织位置可得的域）**。例如同为「采购/渠道」角色：普通采购员（组织位置=组员）只能看 SELF；采购一组组长（组织位置=负责人）自动扩到本组及下级。资源侧通过**归属人字段**（供应商的引入人 `owner_procurement_operator_id`、客户的归属销售 `owner_sales_operator_id`）做行级过滤。

> **本期新增决策（与 PRD §2.2 的差异，以本版为准）**：
> - **D33**：采购/渠道数据域 = 仅本人引入的资源（SELF），主管 = 本部门及下级；PRD 原设计为「供应商与成本域全量可见」，权限矩阵对应行需修订。
> - **D34**：设「运营管理员」角色，可见所有客户与资源（ALL，只读为主）。
> - **D35**：客户/供应商档案新增付款方式、授信额度、押金三类商务属性及联动冻结规则。
> - **D36**：客户门户从被动收单升级为可登录自助门户；三门户登录方案落地。

> **v1.4 补充裁定 · D33 与比价用例的边界（原冲突 R-07）**：采用「**放开比价、收窄商务**」。
> - **放开 ALL**：成本视图、多供应商比价、市场最低价、议价机会、报价异常检测（D2/D4）——比价属于平台级市场信息，SELF 域下"市场最低价"这个比较基准不存在，用例无法成立。
> - **收窄 SELF**：供应商档案的商务字段（结算方式/账期/最低起充/保证金/后付额度）、报价单审批、报价单明细金额。

| F 运营工作台 | 待办与看板 | 按角色聚合待办（数量角标/优先级/超时高亮）、角色化指标卡 | **MVP** |
| F | 告警中心 | 告警源归一、订阅/路由（站内+邮件/IM）、标记处理、转工单、超时升级 | **MVP**（IM 推送 P1） |
| F | 审计查询 | 多维筛选、变更前后值对比视图、影响追溯、导出 | **MVP** |

> **MVP 刻意不做自动抓价**：抓价的工程量和维护成本很高，手工录入几百个主力模型的价格一次也就半天。先把两条定价线跑通产生业务价值，P1 再补自动化（决策点 1 已确认）。

**「已生效」的下游连锁逻辑（关键，全部自动触发）**：

1. **新建不可变官方价版本**：关闭旧版本生效期，官方价变更时间线全量可查（谁、何时、来源、置信度、触发任务 ID）。
2. **供应商倍率报价自动跟随**：展示层按新官方价实时重算（零重录）；同时自动落一条带触发原因的不可变静默版本（`trigger=official_price_change`，记录原值/新值），计入报价历史可逐条查询。绝对价（价格模式）报价不自动跟随，需供应商主动修订。
3. **标准成本真实重算上涨**：内部成本数据必须反映真实情况，不得为"账面好看"而冻结成本。
4. **受影响对外价目表自动冻结**：不立即跟涨，触发告警给定价运营，附"若跟涨，各客户档位毛利影响"预演。
5. **通知期内人工决策（半自动传导）**：
   - **跟涨**：定价运营手动确认新价目表（差异报告 + 影响客户清单），走双人审批发布流程，生成客户涨价通知任务（带提前期，如 30 天）；引用旧价目表的客户报价被标记「需刷新」，销售手动确认。
   - **不跟涨**：维持冻结价售卖，系统持续高亮「售价-成本倒挂」风险直至解决。
6. **合同价保护**：已签合同客户合同期内不调价，官方涨价与合同价的差额由平台承担，到期后按新价目表执行。

## 7 非功能需求

| 维度 | 要求 |
| --- | --- |
| 数据量级 | 模型 SKU 5000+，供应商 100+，报价明细 50 万+ |
| 查询性能 | 价目表查询 P99 ≤ 50ms（下游高频拉取，建议全量缓存 + 事件失效） |
| 精度 | 价格字段 Decimal，禁用浮点；单价保留 8 位小数；统一内部计价单位「每百万 token」 |
| 币种与税务 | 币种跟随模型（海外 USD 不含税 / 国内 CNY 含税）；成本/售价/毛利在模型币种内核算不统一折算；汇率固定 8 档 + 每月锁定 |
| 时区 | 统一 UTC 存储，展示按用户时区；生效时间按 Asia/Shanghai 判定 |
| 幂等 | 同步任务、报价提交、价目表发布均需幂等 |
| 权限 | 字段级权限控制（成本、毛利字段对销售/供应商物理不可见） |
| 审计 | 价格相关操作 100% 留痕，保留 3 年 |
| 技术栈建议 | 模块化单体 + **PostgreSQL 15**（逐组件价格独立成表；非结构化参数用 JSONB）+ **Redis 7（可选，仅短信验证码与登录限次，非强依赖）**+ 对象存储；单台 CVM 部署（nginx + Go 单进程 + PostgreSQL），事件分发用数据库任务表 + 后台轮询 |
| 时区 | 统一 UTC 存储，展示按用户时区；生效时间按 Asia/Shanghai 判定（与设计文档一致） |
